# R0.1 — Portable Static Core

Status: **PROPOSED**  
Milestone type: **public infrastructure + first executable vertical slice**

## Objective

Establish the minimum public open-source infrastructure required for QR Commons to own a portable, deterministic static QR authoring core without inheriting product-specific assumptions from any prior implementation.

R0.1 is not a migration. It is a re-derivation of the smallest useful contracts from standards, observable behavior, and lessons learned in prior implementations.

Just as importantly, R0.1 establishes the project's adoption posture: QR Commons should begin life as infrastructure that can be evaluated, audited, integrated, self-hosted, and maintained—not merely as code that happens to generate QR symbols.

## Outcome

R0.1 should prove this pipeline:

```text
text payload
  -> encode
  -> immutable QR symbol/matrix
  -> deterministic SVG
  -> conformance checks
```

The result must work without accounts, hosted redirects, network payload processing, React, Next.js, browser storage, or a QR Commons backend.

## Infrastructure established in R0.1

### Technical

- supported runtime policy;
- strict TypeScript baseline;
- pnpm workspace policy;
- package-boundary rules;
- dependency admission rules;
- deterministic test fixtures;
- independent decode/conformance strategy;
- CI compatibility targets;
- public trademark and dependency notices;
- provenance/re-derivation rules for behavior learned elsewhere.

### Public OSS adoption

- public-infrastructure quality model covering correctness, determinism, portability, privacy, supply chain, conformance, compatibility, and operational usability;
- security reporting and coordinated-disclosure posture;
- lightweight transparent governance;
- explicit community/support expectations;
- English canonical technical language;
- Spanish as the first officially maintained translation language;
- English/Spanish project and contributor entry points.

## Executable scope

### `packages/core`

Owns the canonical QR symbol model and default encoding behavior.

R0.1 responsibilities:

- text payload input;
- error-correction level L/M/Q/H;
- immutable borderless matrix;
- symbol size and derived QR version;
- deterministic behavior;
- typed domain errors.

The encoder implementation is an internal dependency detail. Consumers do not receive or depend on the third-party encoder API.

### `packages/renderer`

Owns matrix-to-artifact rendering.

R0.1 responsibilities:

- deterministic SVG;
- square modules only;
- standards-safe quiet zone, defaulting to four modules;
- foreground/background colors under a deliberately small configuration contract;
- no DOM requirement.

### Conformance harness

Cross-package tests verify:

- matrix dimensional invariants;
- deterministic output;
- representative payload fixtures;
- encode/decode roundtrip using an implementation independent from the runtime encoder;
- renderer output invariants;
- absence of required network behavior.

The conformance corpus is treated as part of the public project's value: it should make implementation changes and future encoder replacement safer and independently assessable.

## Reserved, not yet promoted to public packages

### `packages/formats`

Remains reserved until structured payloads such as Wi-Fi, vCard, email, phone, and SMS create a real adapter API.

### `packages/validator`

Remains reserved until QR Commons has a user-facing preflight/quality API that is meaningfully distinct from package-local invariant checks and the conformance test harness.

This avoids manufacturing package boundaries before behavior justifies them.

## Explicit exclusions

R0.1 does **not** include:

- logos;
- rounded/circular modules;
- custom finder styling;
- PNG/raster export;
- presets;
- batch generation;
- dynamic redirects;
- analytics or scan telemetry;
- accounts or persistence;
- campaign management;
- npm publication;
- release provenance/SBOM automation;
- a production-grade web authoring UI.

These are deferred deliberately, not forgotten.

## Re-derivation rule

Prior implementation code is reference material, not source material.

For every capability:

1. identify the behavior worth preserving;
2. verify the behavior against public QR requirements where applicable;
3. define a QR Commons-owned contract;
4. implement the contract independently;
5. add fixtures/tests that describe the behavior;
6. only then consider feature parity with prior tooling.

No organization-specific routing, branding, auth, telemetry, resolver logic, or UI composition crosses into QR Commons.

## Acceptance

R0.1 is complete when:

1. identical canonical inputs produce identical matrices and SVG strings;
2. text payloads roundtrip through an independent decoder for representative fixtures;
3. generated symbols use valid QR dimensions (21..177 modules, +4 per version);
4. SVG output enforces at least a four-module quiet zone;
5. `core` and `renderer` execute in both browser-compatible ESM and supported Node runtimes without DOM dependencies;
6. CI verifies supported runtime branches;
7. runtime dependencies and licenses are documented and intentionally small;
8. no package is published to npm accidentally before a separate release decision;
9. security, governance, support, and contribution policies are explicit and public;
10. the project has maintained English and Spanish entry points under the language policy;
11. the public-infrastructure quality model is accepted as a project-wide design constraint rather than aspirational marketing.

## What comes next

R0.2 can build practical authoring capabilities on top of this core: structured formats, browser reference UI, PNG export, and user-facing validation. Styling and logo safety remain later concerns once the standards-correct baseline is proven.

Before stable package distribution, later R0.x milestones should also harden supply-chain controls, release provenance, compatibility evidence, performance/footprint budgets, and package publication policy.
