# ADR-0003 — R0.1 runtime and package baseline

Status: **PROPOSED**  
Date: **2026-09-14**

## Context

QR Commons is becoming a public open-source project rather than an application-specific utility. Its first implementation milestone needs enough infrastructure to be dependable without freezing unnecessary package APIs or adopting infrastructure that only serves a future SaaS/product surface.

Node.js 20 is already end-of-life. Node.js 22 and 24 are current LTS lines as of this decision, while Node.js 24 is the recommended development runtime.

## Decision

### Runtime compatibility

- Supported Node.js lines for package development and CI: **22 and 24**.
- Recommended contributor runtime: **Node.js 24 LTS**.
- Browser-compatible library code must not rely on Node-only globals unless isolated behind an explicit runtime adapter.
- `packages/core` and `packages/renderer` must not depend on the DOM.

### Package manager

- Continue using pnpm workspaces.
- Pin the repository to a concrete pnpm 10.x release during R0.1 rather than implicitly following a new major.
- Commit a lockfile when executable R0.1 dependencies are introduced.

### Language/tooling

- TypeScript with strict checking is the source-language baseline.
- ESM is the canonical module format for R0.1 source and tests.
- Library packages should compile without a framework-specific build step.
- Vitest is the preferred package/conformance test runner once executable code lands.
- No bundler is constitutional. A bundler may be added only if distribution requirements demonstrate a need.

### Package publication

- Workspace packages remain `private` during R0.1.
- Public GitHub source does **not** imply a stable npm API.
- npm publication, package naming, provenance signing, release automation, and semantic-versioning guarantees require a later explicit release ADR.

### Package topology

R0.1 promotes only two executable boundaries:

1. `packages/core` — canonical symbol model + default encoder implementation;
2. `packages/renderer` — deterministic SVG rendering from a QR Commons symbol/matrix.

`packages/formats` and `packages/validator` remain reserved but are not promoted into public package contracts during R0.1.

## Consequences

### Positive

- avoids supporting an EOL runtime at project birth;
- keeps browser and Node consumers possible;
- reduces premature package/API fragmentation;
- allows the encoder and renderer to evolve independently;
- avoids coupling library design to the reference web application;
- prevents accidental npm publication of pre-alpha contracts.

### Costs

- consumers cannot yet install stable QR Commons packages from npm;
- a later release milestone must decide distribution/bundling details;
- contributors on Node 20 must upgrade before working on the repository.

## Rejected alternatives

### Node.js >=20
Rejected because Node 20 reached end-of-life in March 2026.

### Adopt the newest major of every tool immediately
Rejected. Public OSS infrastructure benefits more from deliberate compatibility than from treating every new tool major as an architectural requirement.

### Publish every planned package from day one
Rejected. Empty package boundaries create coordination cost and false API commitments before behavior exists.

### Put QR logic in the web application first
Rejected. The hosted tool is a consumer of the QR Commons libraries, not their source of truth.
