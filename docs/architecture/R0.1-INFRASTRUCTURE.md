# R0.1 Infrastructure Architecture

Status: **PROPOSED**

This document translates the R0 project charter into the infrastructure that the first executable milestone should actually establish.

## 1. Design target

QR Commons should be usable as a library before it becomes a polished hosted application.

The canonical dependency direction is:

```text
                     public standards / behavior
                               |
                               v
                        packages/core
                     text -> QR symbol
                               |
                               v
                     packages/renderer
                     symbol -> SVG string
                               |
              +----------------+----------------+
              |                                 |
              v                                 v
        conformance tests                   apps/web
       independent checks                reference consumer
```

Nothing below `apps/web` may depend on React, Next.js, authentication, analytics, routing, browser storage, or a hosted API.

## 2. Canonical model

R0.1 should introduce a QR Commons-owned symbol representation rather than passing dependency-native data through the system.

Conceptually:

```ts
interface QrSymbol {
  readonly matrix: QrMatrix;
  readonly size: number;
  readonly version: number;
  readonly errorCorrection: "L" | "M" | "Q" | "H";
}

interface QrMatrix {
  readonly modules: readonly (readonly boolean[])[];
  readonly size: number;
}
```

The exact names may change while R0.1 is in draft, but these invariants should not:

- square boolean matrix;
- standard QR dimensions from 21 to 177 modules;
- version derived from dimension, not guessed by UI code;
- no quiet zone embedded in the matrix;
- no styling embedded in the symbol;
- no URL/redirect semantics embedded in the symbol.

## 3. Encoder boundary

`packages/core` owns the public encoding behavior.

The default implementation may delegate bit-level QR construction to a small third-party encoder. The adapter must normalize all dependency output immediately into QR Commons-owned data.

The adapter boundary exists to ensure that:

- consumers never import the dependency;
- dependency error strings never become the public API accidentally;
- border/quiet-zone behavior stays explicit;
- upgrades can be tested against the same behavioral fixtures;
- another encoder can replace it later without redesigning the renderer.

## 4. Renderer boundary

`packages/renderer` consumes only QR Commons symbol/matrix data.

R0.1 SVG deliberately supports the boring case first:

- square dark modules;
- square finder patterns as encoded by the matrix;
- configurable foreground/background;
- four-module default quiet zone;
- deterministic serialization;
- no external image references;
- no DOM APIs.

### Why render the matrix faithfully first?

The prior tooling demonstrated that custom module shapes, custom finder reconstruction, and logo masking are possible. They also increase the number of ways a renderer can accidentally diverge from the encoded matrix.

R0.1 therefore proves a literal renderer before introducing controlled transformations in later milestones.

## 5. Quiet-zone ownership

The quiet zone is a rendering concern, not an encoding concern.

The core symbol remains borderless. The renderer adds the quiet zone explicitly, with four modules as the minimum/default for standard QR Code.

This makes physical/output policy visible and keeps the encoded symbol representation independent of export format.

## 6. Validation architecture

R0.1 has two different forms of validation and should not confuse them.

### Package-local invariants

`core` validates its own input and symbol invariants. `renderer` validates its own render configuration.

These checks are part of each package contract.

### Conformance

Repository-level conformance tests ask whether the composed system behaves correctly across package boundaries.

Conformance should cover:

- representative ASCII and UTF-8 text payloads;
- short and capacity-boundary cases;
- all four error-correction levels;
- deterministic matrix output;
- independent decode roundtrip;
- deterministic SVG output;
- quiet-zone geometry;
- absence of runtime network requirements.

This is why a separate public `validator` package is not yet required.

## 7. Error model

Do not recreate a single cross-repository error class that owns every possible failure.

R0.1 should prefer package-local typed errors/codes:

```text
core
  EMPTY_PAYLOAD
  PAYLOAD_TOO_LARGE
  ENCODING_FAILED
  INVALID_SYMBOL

renderer
  INVALID_COLOR
  INVALID_QUIET_ZONE
  INVALID_SYMBOL
```

Shared error infrastructure should only appear if repeated consumer behavior proves it necessary.

## 8. Runtime policy

### Library code

- ESM;
- DOM-free core and renderer;
- Node 22 and 24 compatibility target;
- browser bundler compatibility;
- no filesystem requirement;
- no environment variables;
- no network access.

### Development

- Node 24 LTS recommended;
- pnpm 10.x pinned during R0.1;
- strict TypeScript;
- Vitest for unit/conformance tests once code lands.

### Web app

The reference web app is intentionally downstream. R0.1 may add a smoke consumer later, but architecture is not allowed to bend around Next.js or any other web framework.

## 9. Test strategy

### Layer A — domain/invariant tests
Fast package-local tests for input, dimensions, immutability, error codes, and deterministic output.

### Layer B — golden fixtures
Small reviewed fixtures capture payload + ECC + expected structural metadata. Golden data should test behavior, not freeze third-party implementation internals unnecessarily.

### Layer C — independent decode roundtrip
Convert generated symbol data into a simple test image/buffer and decode it with a separate implementation lineage. This decoder remains dev/test-only.

### Layer D — browser acceptance
Added when the web consumer exists. Browser tests verify that no QR payload must leave the client and that exported artifacts remain usable.

## 10. Dependency policy for R0.1

Runtime dependencies must be:

- necessary for behavior we do not have strategic reason to reimplement yet;
- compatible with Apache-2.0 distribution;
- usable without accounts, network services, telemetry, or remote assets;
- small enough to audit conceptually;
- isolated behind QR Commons-owned contracts when they implement core behavior.

Dev dependencies may be broader, but must not leak into runtime bundles or public APIs.

No dependency earns constitutional status. Behavioral contracts do.

## 11. OSS repository hygiene

R0.1 should leave behind:

- explicit Node/runtime policy;
- exact package-manager version;
- committed lockfile once dependencies land;
- CI across supported Node LTS targets once executable code lands;
- dependency update automation after the lockfile exists;
- trademark notice;
- clear contribution requirements for new dependencies;
- no release automation until package publication is approved;
- no secrets or environment-specific configuration required for tests.

## 12. What we intentionally do not inherit

From prior product tooling we do **not** inherit:

- component hierarchy;
- application state shape;
- presets;
- auth or protected routes;
- product colors/branding;
- download UX;
- browser-only PNG implementation;
- internal naming;
- dynamic resolver behavior;
- analytics;
- organization-specific defaults.

We inherit lessons, not coupling.

## 13. R0.1 completion shape

At the end of R0.1 the repository should feel small:

```text
packages/
  core/
    src/
    test/
  renderer/
    src/
    test/
tests/
  conformance/
docs/
  architecture/
  decisions/
  milestones/
apps/
  web/        # downstream reference surface; not source of truth
```

If substantially more infrastructure is required merely to turn text into a verified SVG, the milestone is probably over-engineered.
